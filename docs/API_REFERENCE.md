# Radar IT Incident Management API Reference

This reference was generated by inspecting the Spring MVC controllers, request/response DTOs, security configuration, exception handler and frontend tree.

## Base URL and conventions

For a local backend using the default Spring port, the base URL is `http://localhost:8080`; API routes begin with `/api`. Replace the host and port if your local configuration differs. JSON enum values are case-sensitive names such as `HIGH`, `P1`, `INVESTIGATING`, `TECHNICIAN` and `ROUND_ROBIN`.

All routes require a valid JWT except `POST /api/auth/register`, `POST /api/auth/login`, and CORS preflight `OPTIONS` requests (permitted globally; they are not business API handlers). Authentication is stateless. Registration creates an Employee account. The API serializes the internal `EMPLOYEE` role as `USER` for compatibility; `TECHNICIAN` and `ADMIN` remain as written.

Unless the route says otherwise, a successful request returns HTTP 200 with the shown JSON. Registration and incident/comment creation return HTTP 201. Successful deletes return HTTP 204 with no body.

## Authentication guide

### Register

`POST /api/auth/register` is public. New registrations are always Employees.

Request:

```json
{
  "name": "Alex Morgan",
  "email": "alex.morgan@example.com",
  "password": "Example-password-42"
}
```

Successful response (201):

```json
{
  "token": "<JWT>",
  "user": {
    "id": 42,
    "name": "Alex Morgan",
    "email": "alex.morgan@example.com",
    "role": "USER",
    "createdAt": "2026-11-19T10:15:30Z"
  }
}
```

### Login

Exact login URL: `POST http://localhost:8080/api/auth/login`.

Request:

```json
{
  "email": "alex.morgan@example.com",
  "password": "Example-password-42"
}
```

Successful response (200) has the same `AuthResponse` shape as registration. The JWT is in the top-level `token` field; account details are in `user`.

Send the token on authenticated requests as:

```http
Authorization: Bearer <JWT>
```

`GET /api/auth/me` returns the current user's `UserResponse`.

### PowerShell examples

Run these in PowerShell after starting the backend. Supply a real account's credentials locally; do not save the password in source control.

```powershell
$baseUrl = "http://localhost:8080"
$loginBody = @{
  email = "alex.morgan@example.com"
  password = Read-Host "Password"
} | ConvertTo-Json

$login = Invoke-RestMethod -Method Post `
  -Uri "$baseUrl/api/auth/login" `
  -ContentType "application/json" `
  -Body $loginBody

$token = $login.token
$headers = @{ Authorization = "Bearer $token" }
```

Authenticated GET example:

```powershell
Invoke-RestMethod -Method Get `
  -Uri "$baseUrl/api/incidents?page=0&size=10" `
  -Headers $headers
```

Duplicate detection example (use category/service IDs returned by the lookup endpoints):

```powershell
$duplicateBody = @{
  description = "Email server unavailable for all users"
  categoryId = 1
  serviceId = 1
} | ConvertTo-Json

Invoke-RestMethod -Method Post `
  -Uri "$baseUrl/api/incidents/duplicate-suggestions" `
  -Headers $headers `
  -ContentType "application/json" `
  -Body $duplicateBody
```

Unauthorized request example (no token; expect HTTP 401):

```powershell
try {
  Invoke-RestMethod -Method Get -Uri "$baseUrl/api/auth/me"
} catch {
  $_.Exception.Response.StatusCode.value__
}
```

## Common errors

The normal error response is `ApiError`:

```json
{
  "timestamp": "2026-11-19T10:20:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "fieldErrors": {
    "description": "Description is required"
  }
}
```

`fieldErrors` may be `null` when the error is not a field-validation error. Error handling implemented centrally:

| HTTP | Meaning in this backend |
|---|---|
| 400 | Bean validation failure, malformed JSON/enum, invalid query parameter type, or a `BadRequestException` rule (e.g. an unsupported sort field or priority mismatch). |
| 401 | Missing/invalid JWT for a protected route, or bad login credentials. |
| 403 | Authenticated caller lacks a required role or access to another Employee's incident. |
| 404 | Incident, user, technician, category, service, or other requested resource was not found; also unknown URL. |
| 409 | Conflict/business rule (e.g. duplicate registration email, invalid lifecycle transition, unavailable/overloaded technician, ineligible operation). |

Unexpected infrastructure errors may result in a server error; their exact response is not normalized by the controller advice.

## Endpoint reference

Role labels below mean Employee (`USER` in JSON), Technician, and Admin. “Any authenticated role” means all three account roles. Incident visibility is narrower for Employees: they can access their own incidents; staff can access all incidents. Method-level role checks are listed as implemented. Every route not marked public still requires JWT because the security filter chain requires authentication globally.

## Search, filtering and reporting

There is no separate reports controller. Incident search/filtering is `GET /api/incidents`; technician capacity reporting is `GET /api/technicians/workload`; notification history is `GET /api/notifications`. Incident list filters are `priority`, `status`, `categoryId`, `technicianId`/`assigneeId`, and case-insensitive description `search`. Pagination is `page`/`size`; sorting supports `createdAt`, `priority`, `status`, `description`, and `id`, with `asc` or `desc` direction.

## SLA monitoring and escalation

The backend implements SLA policy lookup (`GET /api/sla-policies`) and background SLA monitoring/escalation services, but inspection found no REST controller or HTTP endpoint to start monitoring, inspect escalation records, or manage escalation rules. Monitoring is scheduler/service driven. Do not infer an API route for those capabilities.

## Frontend coverage and implementation status

The repository's `frontend` directory currently contains only `.gitkeep`; it has no application source files or API calls. Therefore none of the listed endpoints are currently connected to a frontend in this checkout. This is a repository observation, not a claim about any separately deployed frontend.

The following behaviors are implemented but worth knowing when using the API:

- Registration always creates an Employee; role escalation is a separate Admin-only operation.
- Priority and assignment strategy selection are held in memory and are not persisted by the strategy endpoints; defaults are configured in application properties and selections reset on application restart.
- Duplicate detection returns suggestions only; it does not merge or alter incidents.
- Status transitions are enforced by the lifecycle rules. The API does not provide a generic bypass for illegal transitions.
- No endpoint was found for CRUD management of SLA policies or direct SLA/escalation administration; only SLA policy lookup is exposed.
